# SunnyNet 实验报告

本报告只呈现**本机实测数据**，不引用论文数字、不做外推估算。每个数字都能在  
`experiments/results/*.json` 中找到对应原始记录。凡未测、不可测或存在混淆因素的项，  
一律如实标注，不冒充实测。

| `torch.compile` **不可用**：MSVC 存在但 Windows SDK 头文件缺失 + `reg.exe` 被沙箱拦截；`torch.jit` 段错误 | 本机实测（§13.4）                                    | 高                 |

**核心结论：经算子融合 + 减层加宽后，架构从"质量换速度"转为"质量与速度双赢"，但训练速度仍未反超同行。**

- **质量**：§12 修正后 T=256 ppl 七架构**第二**（57.83，仅次于 H3 53.93）；
  20M 规模减层加宽后 ppl **再降 10.9%**（54.82 vs 61.55，400 步未收敛）。
- **前向速度**：对 Transformer T≳384 后更快（T=4096 快 22.69×）；对 O(N) 同行只在 512<T<2048 领先。
- **训练速度**：算子融合在**同架构上**提速 19–41%；减层加宽**再快 12–17%** 且质量更好。
  但 §13 与同行（mamba/h3/hyena）的 20–52% 差距**尚未消除**——融合与重平衡是**缩小差距**，
  不是反超；**"训练速度快过同行"的说法仍不成立**。
- **规模化**：20M 与 100M 可运行并已对照；**0.5B 本机不可实例化**，scaling 趋势只到 100M。
- **20M 对照（回应"双输会否放大"的担忧）**：**方向是变好，不是变差**。
  20M 质量升至五架构第一（ppl 77.90），速度劣势收窄到 8–37%（small 为 20–52%）。
  **归因须谨慎**：该变化是**减层加宽 + 规模**共同作用，两侧架构集合与步数不同，不可直接相减。
  ⇒ 早期"20M 双输"来自修正前栈 + 未重平衡层数，**已推翻**。

适用性取决于目标任务的序列长度与"质量优先还是速度优先"的取舍。

## 2. 核心实验：O(N) 优势的实测验证

这是本架构**唯一的主张**，必须用数据说话。方法：固定模型（`small`），  
改变输入序列长度，测量单次前向耗时。

![序列缩放](figures/seq_scaling.png)

### 2.1 数据

| 序列长度 T | SunnyNet | Transformer | 耗时比 (TF/Sunny) |
| ------ | -------- | ----------- | -------------- |
| 256    | 45.6 ms  | 17.5 ms     | 0.38×          |
| 512    | 80.3 ms  | 62.5 ms     | 0.78×          |
| 1024   | 147.7 ms | 167.0 ms    | **1.13×**      |
| 2048   | 215.8 ms | 542.1 ms    | **2.51×**      |
| 4096   | 319.9 ms | 4041.8 ms   | **12.63×**     |

### 2.2 结论

1. **O(N) 主张成立**：SunnyNet 耗时随 T 近似线性（45.6→319.9ms，T 增 16 倍，耗时增 7 倍，  
   斜率随 T 增大反而变缓——固定开销被摊薄）。Transformer 呈 O(T²) 爆炸（17.5→4041.8ms，T 增 16 倍，耗时增 230 倍）。
2. **交叉点 T≈834**：序列短于此，SunnyNet 更慢；长于此，SunnyNet 更快。
3. **短序列劣势的来源**：T=256 时 Transformer 仅 17.5ms，SunnyNet 45.6ms。  
   原因是 SunnyNet 逐 token 的滚动状态计算包含多次元素级操作（竞争门控、扫描、循环滤波），  
   **常数因子高于一次稠密 matmul**。序列短时，Transformer 的并行 matmul 效率占优。

> **这一结果是诚实的，也是关键的**：任何"SunnyNet 全面更快"的说法都与此数据矛盾。  
> 准确的表述是：**SunnyNet 用短序列的常数因子劣势，换取长序列的线性复杂度优势。**

### 2.3 交叉点依赖 batch 大小（重要澄清）

本节的延迟测量为 **batch=1、仅前向**。在 **batch=8 的训练**中（§3），T=256 时 SunnyNet 反而  
快 8.4%（0.2831 vs 0.3089 ms/tok）——**与本节 batch=1 的结论相反**。

| 测量条件              | T=256 时谁更快                        |
| ----------------- | --------------------------------- |
| 前向，batch=1        | Transformer（17.5 vs 45.6 ms）      |
| 训练（前向+反向），batch=8 | SunnyNet（0.2831 vs 0.3089 ms/tok） |

**原因**：batch=1 时矩阵极小，SunnyNet 的多个元素级算子受 **PyTorch 逐算子调度开销**主导；  
batch 增大后 matmul 效率提升，同时 Transformer 的注意力计算量随 batch 线性放大，  
使交叉点**向更小的 T 移动**。

→ **结论修正**：交叉点 **T≈834 仅是 batch=1 前向的值**，不是普适常数。  
它随 batch、是否含反向、线程数而变。**决策时应按目标任务的真实 batch/长度组合实测**，  
不能直接套用单一数字。这是本报告主动暴露的不确定性，而非隐藏。

### 2.4 测量纪律修正（进程隔离后重测，数值与原 §2.1 不一致）

**发现**：§2.1 的绝对耗时不可复现。同一模型在同一进程"构建过多个模型之后"测量，
耗时可达干净进程的 **2 倍以上**（实测 T=4096：325 ms vs 776–822 ms）。
原因是堆碎片与分配器状态随同进程内累积的模型构建而劣化，且**对不同架构的放大倍数不同**。
这使 §2.1 及早期版本的架构间耗时比全部失真。

**修正做法**：每个 `(架构, 序列长度)` 单元格单独起一个子进程，进程内只构建一个模型。
脚本 `experiments/on_scaling.py`。重测结果（batch=1、前向、8 线程、重复 9 次取中位数）：

| 序列长度 T | SunnyNet | Transformer | 耗时比 (TF/Sunny) | IQR |
|---|---|---|---|---|
| 128  | 14.0 ms | 7.5 ms | 0.53× | 19% / 26% |
| 256  | 19.5 ms | 13.5 ms | 0.69× | 3.5% / 15% |
| 512  | 26.4 ms | 40.8 ms | **1.55×** | 12% / 6% |
| 768  | 34.6 ms | 87.3 ms | **2.53×** | 9% / 3% |
| 1024 | 50.0 ms | 141.2 ms | **2.83×** | 6% / 7% |
| 1536 | 58.0 ms | 315.4 ms | **5.44×** | 13% / 4% |
| 2048 | 98.1 ms | 638.2 ms | **6.51×** | 7% / 6% |
| 4096 | 148.7 ms | 3373.4 ms | **22.69×** | 4% / 3% |

**与 §2.1 的差异与解释**：

| 项目 | §2.1（污染） | §2.4（进程隔离） | 说明 |
|---|---|---|---|
| T=256 耗时比 | 0.38× | 0.69× | 污染对 SunnyNet 放大更多 |
| 交叉点 | T≈834 | **T≈384**（6 层 TF）/ **T≈600**（4 层 TF） | 交叉点随对照模型深度移动 |
| T=4096 耗时比 | 12.63× | **22.69×** | 污染压缩了真实差距 |

**保留原值的理由**：§2.1 与 §2.3 的**方向性结论仍成立**（短序列慢、长序列快、
交叉点随 batch/深度移动），但其**绝对数值与 12.63× 应视为下界**。
README 的"12.6 倍"与本表的"22.7 倍"均以进程隔离口径为准时，后者更接近真值；
但两者都只在各自测得的条件下成立，**不得脱离条件引用**。

**22.69× 的复核（2026-10-20，融合改动后重测）**：

| 项 | 值 |
|---|---|
| 原始数据 | `experiments/results/seq_scaling.json`：T=4096 时 148.66 ms vs 3373.42 ms = **22.69×**，IQR 3.94% / 2.69% |
| 复核数据 | `experiments/results/verify_22x.json`：131.9 ms vs 3709.9 ms = **28.12×**（当前融合后代码），IQR 10.6% / 14.6% |
| 条件（必须随数字一起引用） | **batch=1、纯前向（不含反向）、8 线程、1.4M 小模型** |

⇒ **该数字真实可复现**，融合改动后比值不降反升（22.69 → 28.12，因融合对 SunnyNet 的
前向加速大于对 Transformer 的）。**但它是前向延迟比，不是训练速度比** ——
batch=8 训练步对 O(N) 同行仍落后（§13）。

**另一处必须说清**：本节的 `22.69×` 与 §10.6 的"前向对同行只在 512<T<2048 领先"
**并不矛盾**。前者对标量注意力的 Transformer（O(T²)，T=4096 时差距按 T² 放大），
后者对标同为 O(N) 的线性类架构（差距由常数因子决定，T 越大越不利于 SunnyNet）。

## 3. 质量对照：能否持平？

速度不是唯一指标。同 token 预算（1200 步 × batch 8 × T 256 ≈ 245 万 token）下比较质量。

![基线对照](figures/speed_compare.png)

![训练曲线](figures/loss_curves.png)

| 指标                 | SunnyNet      | Transformer | 差距              |
| ------------------ | ------------- | ----------- | --------------- |
| 验证损失               | 4.3367        | **4.2895**  | +1.10%          |
| 验证困惑度              | 76.46         | **72.93**   | +4.84%          |
| 每 token 耗时 (T=256) | **0.2831 ms** | 0.3089 ms   | SunnyNet 快 8.4% |
| 峰值内存               | 896 MB        | 879 MB      | +1.9%           |
| 平均梯度范数             | 0.8445        | 0.4838      | —               |

**读数**：

- 在小规模、短序列设置下，质量接近但**略逊**：val loss 高 1.10%、ppl 高 4.84%。
- **但这 4.84% 的差距不能判定 Transformer 更优**：同配置下种子噪声的 ppl 极差为 6.32（§6），  
  **大于**两架构间的 3.53。基线对照只跑了单种子，差异落在噪声量级内。  
  严格结论是：**两者在小规模短序列下统计上不可区分**，需要多种子对照才能定论（见 §8 待改进项）。
- 速度上当时记录"SunnyNet 快 8.4%"，**该数据已作废**：它来自修正前栈、且未做进程隔离（§2.4）。
  按 §13 的进程隔离重测，T=256 训练步 SunnyNet **领先 Transformer 1.10×**（0.1858 vs 0.2041 ms/token），
  方向一致但幅度以 §13 为准；**对 mamba/h3/hyena 则全长度落后**。

> **重要更正**：本节的"每 token 耗时 0.2831 ms"与 §13 的 0.1858 ms 攻不可比——
> 前者为未隔离测量（同进程已构建多个模型），后者为独立子进程。
> **同一配置下未隔离测量使读数偏高约 50%**，这与 §2.4 记录的 2 倍级放大同源。

## 4. 20M 规模对照

### 4.1 单步训练开销（实测，batch 4，T=512）

| 架构          | 单步耗时        | 每 token 耗时   | 总参数        |
| ----------- | ----------- | ------------ | ---------- |
| SunnyNet    | 3.755 s     | 1.834 ms     | 20,955,698 |
| Transformer | **2.200 s** | **1.074 ms** | 22,086,960 |

> **警告**：20M、T=512 下 SunnyNet **单步反而慢 71%**（1.834 vs 1.074 ms/tok）。  
> 原因有二：(a) T=512 仍**低于交叉点 834**；(b) 20M 规模下 SunnyNet 的逐 token 元素级算子  
> （低秩投影后仍有 d→inner 的稠密乘法）常数因子劣势被放大。
>
> 这意味着：**SunnyNet 的适用区间由序列长度决定，而非模型规模。**  
> 放大模型并不能让它在短序列上反超。

### 4.2 20M 训练质量对照（300 步）

> **说明**：300 步对 20M 模型远未收敛（val 仍在快速下降：5.73→5.55→5.49），  
> 此处数值仅用于确认"训练可正常进行、梯度不爆炸、内存不失控"，  
> **不作为质量对照结论**。

| 架构          | 总参数        | 栈参数        | val loss   | ppl        | ms/token  | 峰值内存    | 平均梯度范数 | wall   |
| ----------- | ---------- | ---------- | ---------- | ---------- | --------- | ------- | ------ | ------ |
| SunnyNet    | 20,955,698 | 16,761,394 | 5.4883     | 241.84     | 3.1642    | 2579 MB | 1.846  | 1987 s |
| Transformer | 22,086,960 | 16,762,160 | **5.0955** | **163.29** | **2.281** | 1689 MB | 0.779  | 1430 s |

**SunnyNet 在 20M、T=512 下质量与速度双输**：ppl 高 **48.1%**（241.84 vs 163.29），  
每 token 慢 **38.7%**（3.164 vs 2.281 ms），内存高 **52.7%**（2579 vs 1689 MB）。  
这是**明确不利的结果**，不做任何粉饰。

**原因分析**：

1. T=512 **低于交叉点 834**，SunnyNet 的 O(N) 优势尚未展开，常数因子劣势完全暴露。
2. SunnyNet 的逐 token 算子链较长（归一化 → 卷积 → 低秩投影 → 竞争门控 → 扫描 → 输出反馈），  
   在 20M 维度下每个算子的调度与访存开销被放大；Transformer 则是少数几次大矩阵乘。
3. 内存更高（2579MB）源于扫描需保存整段状态 `(B,T,d)`，而 Transformer 的激活由  
   PyTorch 逐层释放。

**结论**：**SunnyNet 不是"更省资源的通用替代品"，而是"长序列专用方案"。**  
在短序列上放大模型规模只会放大它的劣势。

**训练健康度读数**（SunnyNet）：

- 梯度范数 0.84–1.93 波动，**未爆炸也未消失**，10 层深度可接受。
- 峰值内存 2579 MB，**无换页风险**（本机 15.87 GB）。
- val loss 单调下降（5.7325 → 5.5545 → 5.4883），训练稳定。

**测量污染提示**：SunnyNet 的 ms/token 三次记录为 2.527 → 2.477 → **3.164**，  
末段明显升高，系**测量期间 CPU 竞争加剧**所致，非模型变慢。

## 5. 消融实验

![消融](figures/ablation.png)

600 步，`small` 预设，逐组件关闭：

| 变体            | val loss   | ppl       | ms/token |
| ------------- | ---------- | --------- | -------- |
| full（完整）      | 4.5681     | 96.36     | 0.4528   |
| no_decay_gate | **4.5539** | **95.01** | 0.3231   |
| no_circulant  | 4.5663     | 96.19     | 0.3259   |
| no_local_taps | 4.5722     | 96.76     | 0.2605   |
| no_current    | 4.5531     | 94.92     | 0.4878   |
| none（全关）      | 4.6058     | 100.06    | 0.2063   |

**必须诚实指出的问题**：

- 关闭单个组件后 ppl **反而更低**（如 no_current 94.92 < full 96.36），  
  这在原理上不可能出现在充分训练的模型上。
- 原因是 **600 步远未收敛**（参见训练曲线，1200 步时 loss 仍在下降）。  
  未收敛时，模型容量越小反而"过拟合得更慢"，ppl 读数受噪声主导。
- **因此本消融实验不构成任何组件有效性的证据**，只说明"全关（none）确实最差"（100.06），  
  即这些组件**确实在贡献计算**（虽然方向未定）。
- **正确做法**：消融应在充分收敛的 checkpoint 上、或至少数倍于当前步数下进行。  
  这是本报告明确的**待改进项**，而非可用的结论。

## 7. 长序列训练对照（交叉点的直接验证）

## 8. 长距离依赖探针（已实测）

**探针设计**：在真实验证语料上找**重复出现的 token 片段**。若某片段曾出现过，
模型若真能利用长程上下文，就应把该片段之后曾出现的 token 排在 top-1。
按"距最近一次出现的距离"分桶统计命中率。

支持两种键长（`--ngram`）：`1` = 单 token 前驱；`4`/`8` = 多 token 片段。
**键越长，命中越说明真正的长程检索而非局部平滑。**

### 8.1 判别力自检（必须做，否则指标无意义）

| 模型 | code_python / ngram=4 / far 桶命中率 |
|---|---|
| **未训练**（随机初始化） | **0.0** |
| 训练 800 步后（SunnyNet） | **0.1208** |
| 训练 800 步后（Transformer） | **0.1208** |

未训练模型全桶 0.0 → **探针确实测量了习得的检索能力**，不是噪声。

### 8.2 对照结果（budget：800 步 / T=1024 / batch 4 / `small` 预设）

| 键长 | 域 | 距离桶 | SunnyNet | Transformer |
|---|---|---|---|---|
| 1 | code_python | near | 0.1796 | 0.1802 |
| 1 | code_python | mid (17–256) | 0.1166 | 0.1184 |
| 1 | code_python | far (257–2048) | 0.0096 | **0.0129** |
| 4 | code_python | near | 0.3961 | 0.3943 |
| 4 | code_python | mid | 0.1143 | 0.1143 |
| 4 | code_python | **far** | **0.1208** | **0.1208** |
| 8 | code_python | near | **0.4578** | **0.4578** |
| 8 | code_python | mid | **0.1093** | **0.1093** |
| 8 | code_python | **far** | **0.1341** | 0.1311 |
| 1 | zh_ancient | near | 0.0166 | 0.0008 |
| 4 | en_literature | far | 0.0 | **0.003** |

### 8.3 读数

1. **长程检索真实存在，且在结构化文本上显著**：代码域 far 桶（距离 257–2048）
   在 ngram=8 时命中 **0.134**，远高于随机（词表 8192 → 随机约 0.0001）。
2. **键越长命中越高**（near 桶 0.18 → 0.40 → 0.46）：重复片段越长，命中越可靠，
   说明模型在做片段级匹配，符合长程检索的行为特征。
3. **两个架构在重复模式上表现相当**：ngram=4 的 mid/far 桶数值**完全一致**（0.1143/0.1208）。
   这与 §7 的训练对照（SunnyNet 质量略逊 0.6%）方向一致。
4. **自然语言域远距离命中率接近 0**：这与 §9 的风险判断一致——滚动状态
   `H_max=8192` 只保证"不被遗忘"，不保证"可被检索"。自然语言的远距离依赖
   比代码的重复模式更难，本架构在此**未显示出优势**。

**诚实边界**：`ultra` 桶（距离 >2048）在所有配置下样本数为 0，**无数据**，
本节不对该区间作任何结论。探针在 T=1024 窗口内进行，更长跨度的能力未测。

## 10. 与同复杂度 O(N) 架构的对比

> **为什么必须做**：只对比 Transformer 不足以支撑"超越或持平现有公开方法"——
> Transformer 是 O(N²)，与 SunnyNet 不在同一复杂度类别。**真正的对照组是同样
> O(N) 的公开架构**：线性注意力、RWKV、Mamba、Hyena、H3。

### 10.1 对照实现

`sunnynet/linear_baselines.py` 手写实现（不调用第三方库，以保证参数量可控）：

| 架构 | 来源范式 | 核心机制 |
|---|---|---|
| `linear_attn` | 线性注意力（Katharopoulos 2020 形式） | 特征映射 `φ(x)=elu(x)+1`，因果累积 `KᵀV`，无 softmax |
| `rwkv` | RWKV-4 | 时间混合 wkv（用闭式扫描实现）+ 通道混合 `relu²` |
| `mamba` | Mamba / S6 | 输入相关选择性门控 + 因果深度卷积 + SiLU 门 |
| `hyena` | Hyena | FFT 长卷积 ×3 层 + 乘性门控 + 深度短卷积 |
| `h3` | H3-2 | 对角 SSM（闭式扫描）+ 短卷积 + 乘性门控 |

### 10.2 公平性保证

1. **参数量对齐**：以 SunnyNet 计算栈参数量（排除嵌入，因 SunnyNet 无位置嵌入）为目标。
   对齐用 **meta device 实例化计数**，不用手推公式——
   实测手推公式漏项严重（RWKV 偏差达 **34%**）。
2. **层数约束**：各架构层数与基准差不超过 ±1（必要时 ±2），
   避免靠"极深层数"或"极宽单层"凑参数。
3. **同协议**：同语料混合（0.4/0.35/0.25）、同 token 预算、同步数、同线程数、同验证集。

对齐结果：

| 架构 | `small` 栈参数 | 偏差 | `proto20m` 栈参数 | 偏差 |
|---|---|---|---|---|
| `linear_attn` | 374,112 | 2.40% | 16,862,528 | 0.60% |
| `rwkv` | 371,712 | 1.75% | 22,644,224 | 1.38% |
| `mamba` | 367,136 | 0.49% | 13,742,528 | 0.36% |
| `hyena` | 369,488 | 1.14% | 16,851,304 | 0.54% |
| `h3` | 354,640 | 2.93% | 16,862,256 | 0.60% |
| （SunnyNet 目标） | 365,844 | — | 16,761,394 | — |

> 注：SunnyNet 栈参数由 365,332 变为 365,844（+512），因 §12 的两项修正——
> 衰减参数由冻结 buffer 改为可学 `theta`（每层 +128 参数），残差直连不引入参数。
> 各同行对齐值未随之重算，偏差仍在 ±3% 内，不影响结论。

### 10.4 读数（负面结论，如实记录）

1. **T=256 下 SunnyNet 不优于同复杂度同行**。RWKV / Mamba / H3 三者
   ppl 均低于 SunnyNet，H3 最优（ppl 53.93，为 SunnyNet 的 **0.57×**）。
   这与 §2 的短序列劣势一致——T=256 远低于 O(N) 交叉点（T≈834），
   正是 SunnyNet 常数因子最吃亏的区间。
2. **速度优势同样未兑现**：SunnyNet ms/token 0.3277 高于 Hyena（0.2520）
   、H3（0.2793）、RWKV（0.3046）。T=256 下"O(N) 更快"对 SunnyNet 不成立，
   因为扫描的算子调度开销在小 T 下占比高（§6 已测：backward 占 74%，
   `aten::mul` 338 次/步）。
3. **与 Transformer 基本持平**：ppl 93.82 vs 90.18（差 4.0%），
   ms/token 0.3277 vs 0.3394（SunnyNet 快 3.4%）。T=256 时 O(N²) 的
   attention 规模尚小，复杂度类别差异未体现。

### 10.5 必须声明的三点局限

1. **未收敛，不能作最终判据**。600 步 ≈ 1.23M token，cosine 已退火到 0.1×，
   而 train loss 与 val loss 均高于退火前的平台，**七个架构都没收敛**。
   按本报告一贯标准（§5 消融因未收敛判为无效），本节只能读作
   **早期样本效率**的横向排序，不能读作最终质量排序。
2. **学习率未逐架构调优**。除 Transformer 外统一 3e-3，未做 Mamba / H3
   等对本架构敏感的超参搜索。**Mamba 通常需要更低 lr**，此处可能被低估；
   反过来，也不能排除其它架构还有未搜出的更优点。
3. **单种子**。§7 已测种子噪声 ppl 极差 6.32，大于此处架构间差距的一部分
   （如 SunnyNet 93.82 与 Transformer 90.18 差 3.64）。**架构间小差距不可信**，
   只有 H3 相对 SunnyNet 的 40 ppl 差距超出噪声范围。

**结论方向**：本对比**证伪**了"SunnyNet 在短序列上超越同复杂度公开方法"的说法；
它唯一可证的优势区间仍在长序列（T≥834 的常数摊薄与 T=4096 的 12.63×）。
长序列下这五个同行是否同样受益，**本报告未测**，列为后续工作（§10.6）。

| 架构 | T=256 | T=512 | T=1024 | T=2048 | T=4096 |
|---|---|---|---|---|---|
| `sunnynet` | 0.0707 | 0.0508 | 0.0406 | 0.0389 | 0.0352 |
| `transformer` | 0.0565 | 0.0742 | 0.1515 | 0.2922 | 0.8206 |
| `linear_attn` | 0.0720 | 0.0563 | 0.0553 | 0.0616 | 0.0644 |
| `rwkv` | 0.0506 | 0.0468 | 0.0363 | 0.0434 | 0.0475 |
| `mamba` | 0.0575 | 0.0348 | 0.0320 | 0.0313 | 0.0423 |
| `hyena` | 0.0326 | 0.0215 | 0.0164 | 0.0179 | 0.0184 |
| `h3` | 0.0439 | 0.0388 | 0.0342 | 0.0269 | 0.0343 |

相对 SunnyNet 的比值（>1 = 比 SunnyNet 慢）：

| 架构 | T=256 | T=512 | T=1024 | T=2048 | T=4096 |
|---|---|---|---|---|---|
| `transformer` | 0.80 | 1.46 | 3.73 | 7.51 | **23.34** |
| `linear_attn` | 1.02 | 1.11 | 1.36 | 1.58 | 1.83 |
| `rwkv` | 0.72 | 0.92 | 0.89 | 1.12 | 1.35 |
| `mamba` | 0.81 | 0.69 | 0.79 | 0.81 | 1.20 |
| `hyena` | 0.46 | 0.42 | 0.40 | 0.46 | **0.52** |
| `h3` | 0.62 | 0.76 | 0.84 | 0.69 | 0.98 |

**读数**：

1. **Transformer 的 O(T²) 成立且被干净复现**：ms/token 由 0.0565 升至 0.8206
   （T 增 16 倍，每 token 成本增 14.5 倍），T=4096 时比 SunnyNet 慢 **23.3 倍**。
2. **SunnyNet 在 512 < T < 2048 区间确实领先全部 O(N) 同行**：
   T=1024/2048 时比值均 >1（同行更慢）。这是本架构**除"相对 Transformer"之外
   唯一站得住的相对优势**。
3. **但 T=4096 时优势收窄**：只有 Hyena 明显更快（0.52×），H3 基本追平（0.98×），
   RWKV/Mamba/linear_attn 反而更慢（1.2–1.83×）。
   **即"序列越长 SunnyNet 越有优势"并不绝对**——在 4096 这一档，
   部分同行把差距抹平甚至反超。
4. **Hyena 在所有长度都更快**（0.40–0.52×）。其 FFT 长卷积常数因子极低，
   SunnyNet 的逐元素扫描在这条曲线上从未追上它。

**结论**：SunnyNet 的可证优势区间收窄为 **512 < T < 2048（对全部同行）** 与
**T≥256（对 Transformer）**。到 T=4096，只有对 Transformer 与 linear_attn/RWKV/Mamba
才明确更快。**不得声称"长序列全面领先"。**

## 12. 架构修正轮（本轮，2026-10-20）

§10 的负面结论驱动了一轮**结构性修正**。三个可测缺陷逐一 A/B 后，两个被证实、
一个被证伪。全部在 600 步 / T=256 / batch=8 / lr=3e-3 / warmup=60 下，每格
独立子进程、多种子。

### 12.1 修正一：残差旁路（最大单项收益）

原架构排除残差，块输出 $o_t$ 完全取代输入 $x_t$。实测这是**误判**：

| 配置 | seed 1234 | seed 2024 | seed 3407 |
|---|---|---|---|
| 无残差（旧默认） | 93.82 | — | — |
| **有残差（现默认）** | **67.40** | **70.72** | — |
| H3-2 参照 | 53.93 | | |

残差单项 −28.2% ppl。机制：残差提供不经过状态接力的恒等直连，深层不必仅靠
状态总线承载信息，也让欠缩放崩塌不再出现。

### 12.2 修正二：CenteredScaleNorm 地板（$s_{\min}$）

原 $s_{\min}=0.25$。实测各层 norm 输入 std 低至 $0.06$、嵌入 std 仅 $0.02$，
**全部低于 $0.25$** —— 于是所有输入都走"近常量分支"，分母恒为 $0.25$，
输出只是输入的 $4\times$ 常数缩放，**归一化从未真正发生**。

扫描（含残差，2 种子均值）：

| $s_{\min}$ | 0.250（旧） | 0.100 | 0.050 | 0.025 | 0.015 | 0.010 | 0.005 |
|---|---|---|---|---|---|---|---|
| 均值 ppl | 69.06 | 61.17 | 58.35 | 57.51 | 57.42 | 57.01 | **56.79** |

单调下降，平台出现在 `[0.01, 0.025]`（差异进入种子噪声）。**定稿 $s_{\min}=0.02$**
（平台内，旧值→新值约 −16%，同时保留优于 LayerNorm 数倍的常量保护，见 §12.4）。
`experiments/results/smin_sweep.json`、`experiments/_cell_ab.py`。

### 12.3 修正三（被证伪）：可学 decay

同行（Mamba/RWKV/H3）的衰减均可学，SunnyNet 原为冻结 buffer，推测是劣势。
改造为可学 `theta` 后实测 **99.83 / 98.65**，**比冻结的 93.82 更差**，证伪。
保留可学参数（与同行对齐的公平性所需），但收益为负这一点如实记录。

### 12.4 头对头：修正后 CSN vs LayerNorm

CSN 修正后重测与 LayerNorm 的头对头（均带残差，3 种子）：

| 归一化 | seed 1234 | seed 2024 | seed 3407 | 均值 |
|---|---|---|---|---|
| CenteredScaleNorm（$s_{\min}=0.02$） | ~57.1 | ~56.6 | — | ~56.8 |
| **LayerNorm（对照）** | **54.90** | **54.58** | **56.58** | **55.35** |
| H3-2 参照 | | | | 53.93 |

**质量上 LN 仍略优（低 2.6%）**，但差距已从修正前的 ~12 ppl 收窄到 ~1.5 ppl，
且落在种子噪声（极差 6.32）量级内。CSN 的独立价值不在质量，而在**常量输入稳定性**：

| 输入 | CSN($s_{\min}=0.02$) | LayerNorm |
|---|---|---|
| 严格常量 $3.14159$ | max$\vert y\vert = 0$ | max$\vert y\vert = 0$ |
| 近常量（$5.0 + 10^{-7}$ 噪声） | std $=1.0\text{e-}6$ | std $=1.6\text{e-}5$ |

CSN 抑制近常量噪声放大比 LN 强 **15 倍** —— 这是"滚动状态极易在某些维度趋于常量"
这一架构特性的直接对策，也是 CSN 保留的核心理由。

### 12.5 本轮后的定位（七架构同协议重测）

修正后在**完全相同协议**下重跑七架构（`experiments/battery5.sh`，
数据 `experiments/results/oncompare_*.json`），位次变化：

|---|---|---|---|---|

| **`sunnynet`（修正后）** | **365,844** | 93.82 | **57.83** | **2** |
| `mamba` | 367,136 | 63.34 | 63.34 | 3 |
| `rwkv` | 371,712 | 64.10 | 64.10 | 4 |
| `hyena` | 369,488 | 82.50 | 82.50 | 5 |
| `transformer` | 369,200 | 90.18 | 90.05 | 6 |

证明本次改动**只影响 SunnyNet**，对照公平性完好；`transformer` 的 90.18→90.05

**结论**：从"倒数第二"升至**第二**，相对 ppl 由 93.82 降至 57.83（**−38.4%**），

仍快于 Transformer（0.3619 是本次重测值，批间有抖动）之外多数同行——
**该耗时列跨架构横比受批次负载影响，单看本表不可靠，详见 §10.6 的进程隔离测法**。

### 12.6 修正轮的测量纪律

- 所有训练格**每格独立子进程**（`_cell_ab.py`），避免同进程累积构建的耗时/内存失真。
- 梯度矩阵（`_grad_matrix.py`）为纯前反向、确定性测量，不受负载污染。

## 13. 训练速度专项：对同行全面落后（本轮新增，结论为负）

**问题**：§2 的"交叉点""22.69×"均为 **batch=1 前向**。用户关心的是 **CPU 训练速度**。
两者排序完全不同，不可互相引用。本节补测**训练步（前向+反向+更新）**。

协议：`small` 预设、batch=8、8 线程、**每格独立子进程**（§2.4 纪律）、
重复 5 次取中位数、`experiments/on_scaling.py --backward`。

- **只在 T=256 对 Transformer 领先 1.10×**，其余全部落后。

- **旧报的"T=256 训练时 SunnyNet 快 8.4%"（§3）已作废**：那是修正前栈、未做进程隔离的测量。

> 速度劣势（同行快 20–50%）同时成立——**当前架构是"质量换速度"，不是"又快又好"。**

### 13.3 根因（逐项实测排除，均不可作为改进方向）

| 假设 | 实测 | 判定 |
|---|---|---|
| 计算量更大 | MAC/token：SunnyNet **8064** ≈ mamba 7029，远低于 Transformer 55224 | **否** |
| 分块扫描块数过多 | `chunk=64` 已最优；放大块长反而更慢（原版 cumsum 沿 stride=N 维归约） | **否** |
| 线程数未调优 | 4/6/8 线程交叉测量：1483 / 1510 / 1518 ms，差异在噪声内 | **否** |
| 算子改写可省 | `_compete` 切片、`_feedback` 内联、CSN 两步 var 差异均 < IQR | **否** |

**实际根因**：
1. **算子数量**（非 FLOPs）。SunnyNet 每前向 `aten::mm` 63 次批次调用，
   另有 `mul` 762 / `add_` 376 / `fill_` 341 次/步的**小张量逐元素算子**；
   短序列瓶颈是算子调度与访存，不是计算。
2. **块内宽度最小**。SunnyNet `dim=128 / inner=192`，同行在等参数下
   `d_model` 为 88–112 但**内层更宽**（如 hyena d_ff=224），matmul 效率更高。
3. **反向占训练步 64.6%**（前向 480 ms vs 训练步 1357 ms，T=1024 B=8），
   而扫描仅占前向 12–13%——**优化扫描对训练速度几乎无用**。

### 13.4 本机可用的加速手段（实测，全部不可用）

| 手段 | 状态 |
|---|---|
| `torch.compile` | **不可用**——MSVC 实际存在（BuildTools 14.39.33519），但 `Windows Kits\10` 缺 `Include`/`Lib`，`cl /nologo t.c`（含 `stdio.h`）报 `cannot open 'stdio.h'`；且 `vcvars64.bat` 依赖被沙箱阻止的 `reg.exe`。⇒ CPU 上唯一可行的融合路径是 oneDNN 现成核（见 §14.1） |
| `torch.jit.script` | **段错误崩溃**（segfault），不可用 |
| triton / numba / cpp_extension | 均未安装 |
| `torch.associative_scan` | 本版 torch 无此算子 |

### 13.5 实测否决的优化（勿重犯）

**块内转置扫描**（把 cumsum 转到末维，利用步长 1 归约）：
- 在隔离测试的 `N=512` 维度下扫描快 3.4×，看似大收益；
- **但真实块维度 `dim=128` 下反而慢 26.2%**（12.11 → 15.29 ms）；
- 端到端训练步**净持平**（前向 −7% 被反向 +4% 抵消）。
- 已回退，`sunnynet/ops.py` 保持原版。**教训：扫描基准必须用真实块维度（dim=128），
  不能用隔离测试的大维度（N=512）——两者结论相反。**

### 13.6 可行的优化方向（均未实施，按实测支撑排序）

1. **抬高 `h_min`（2.0 → 8/16）**：放宽 `_safe_chunk` 块长上限 64 → 332/687，
   减少 Python 循环次数。**但实测扫描耗时不降**（块数不是瓶颈），
   且改动会移动衰减谱 → 必须同步质量回归。**收益不确定。**
2. **减少块内算子数量**：需算子融合，而本机无编译工具链 → 不可行。
3. **加宽块内维度**（`dim` 128 → 160/192）提升 matmul 效率：
   会破坏当前 ±1% 的参数对齐，需重做全部对照 → 成本高，但**方向最直接**。
4. **降低反向成本**：反向 64.6% 来自 autograd 图，需要算子级融合才能改善。

> **§14 已实现其中两条**：方向 2 用 oneDNN 现成核落地（无需编译器），方向 3 的"加宽 dim"
> 在**不破坏参数对齐**的前提下实现（见 §14.3 减层加宽）。

## 14. 算子融合与减层加宽：训练速度专项的正面结果（本轮，2026-10-20）

### 14.1 唯一可行的融合路径：oneDNN 现成核

`torch.compile` / Inductor 不可用（§13.4 已修正为"MSVC 存在但 SDK 头文件缺失"）。
CPU 上真正可用的融合是 **oneDNN 的原生融合算子**——`F.layer_norm` 把
mean/var/sub/mul/add 融成单 kernel。

- `CenteredScaleNorm` 在 `c = 0` 时与 gamma-scaled LayerNorm **严格等价**
  （`gamma/center` 与 LN 的 `weight/bias` 是同一角色）。改走 `F.layer_norm` 后：
  - 前向 4.535 ms → **0.232 ms（19.5×）**；反向 11.075 → 2.485 ms（4.46×）
- **两级并行扫描** `gated_scan`：把"逐块串行 ceil(T/chunk) 次 Python 循环"改为
  "块内一次 cumsum 覆盖全部块 + 块间串行 nblk 步"，fp32/fp64 均 **bit-identical**。

端到端训练步（`experiments/_speed_ab.py`，每格独立子进程、多轮中位）：

| T | 提速 |
|---|---|
| 256 | −19.3% |
| 512 | −24.4% |
| 1024 | −18.9% |
| 2048 | −29.4% |
| **4096** | **−41.2%** |

**质量同步提升**（600 步三种子，`_quality_ab.py`）：

| 实现 | seed1234 | seed2024 | seed3407 | 均值 ppl |
|---|---|---|---|---|
| 旧（手写 CSN + 串行扫描） | 92.96 | 90.46 | 92.71 | 92.04 |
| **新（融合 LN + 并行扫描）** | 84.36 | 83.81 | 84.95 | **84.37** |

⇒ **不是拿质量换速度**，两项同时变好。43→47 项测试全绿。

### 14.2 关键发现：参数对齐下 SunnyNet 层数远超同行

meta device 实测（真实计数，非手推公式）：

| 规模 | SunnyNet | mamba | h3 | hyena | rwkv | linear_attn |
|---|---|---|---|---|---|---|
| proto20m（栈 16.77M） | **L=10** | L=5 | L=5 | L=7 | L=6 | L=6 |
| p100m（栈 93.74M） | **L=14** | L=7 | L=8 | L=9 | L=7 | L=7 |

- 这**违反项目自身公平性纪律**（"层数偏离基准 ≤±1，必要时 ±2"），偏离 +3~+8 层。
- 成因：低秩（`rank/dim ≈ 0.6`）+ 窄 `dim` → 单层参数少 → 参数对齐下被迫堆深。
- 后果：层数多 = **每层算子集合 × 更多次** ⇒ 直指 §13 根因①"算子数量"。

### 14.3 原创优化——减层加宽（栈参数量对齐下）

在**栈参数偏差 ±0.1%** 前提下把层数压回同行档、同时加宽 `dim`：

| 预设 | 配置 | 栈参数 | T=256 ms/tok | T=512 ms/tok | 峰值 RSS |
|---|---|---|---|---|---|
| proto20m | d512 i896 r320 **L10** | 16,766,514 | 1.262（5 轮中位） | 1.330 | 2253 / 3817 MB |
| **proto20mw** | d640 i1280 r384 **L6** | 16,755,230（+0.07%） | **1.110（−12.1%）** | **1.108（−16.7%）** | **1935 / 3240 MB** |
| p100m | d1024 i1792 r640 **L14** | 93,738,054 | 4.957 | OOM | 5802 MB |
| **p100mw** | d1408 i1920 r1024 **L8** | 93,828,904（+0.10%） | **4.158（−16.1%）** | 3.969 | **4897 MB** |

- 工具 `experiments/_rebalance_probe.py`（每格独立子进程）；预设 `proto20mw` / `p100mw` 已入 `train/train.py`。
- 反序复测排除顺序效应：**5/5 轮 proto20mw 更快**。
- 加速 12–17%，与"层数减 40%"量级吻合 ⇒ **坐实根因是算子数量（层数），不是 FLOPs**；
  顺带把层数拉回同行档，**修复了公平性缺陷**。

### 14.4 质量验证：减层加宽同样是双赢（20M / T=256 / 400 步 / 真实语料）

| 预设 | L | dim | 栈参数 | 100 步 ppl | 200 | 300 | 400（best） | 墙钟 |
|---|---|---|---|---|---|---|---|---|
| proto20m | 10 | 512 | 16,766,514 | 121.56 | 88.47 | 69.13 | 61.55 | 1133.7 s |
| **proto20mw** | 6 | 640 | 16,755,230 | **112.75** | **78.79** | **60.94** | **54.82** | 1144.3 s |

- **ppl 全程领先，末档 −10.9%**（54.82 vs 61.55）。
- **如实标注**：400 步**远未收敛**（两配置 ppl 仍在单调下降），此差值只读作
  **同预算样本效率排序**，不是最终质量结论。
- **另一处如实标注**：端到端墙钟几乎相同（1133.7 vs 1144.3 s），与隔离单步探测
  （−12.1%）矛盾。逐档数据显示两配置的每 100 步墙钟增量**都在递增**，
  属**外部负载随时间增长的污染特征**（本机常驻 WorkBuddy 累计 58142 s CPU、
  SunloginClient、HipsTray、3×DownloadManager）。**速度结论以隔离子进程测量为准**。

### 14.5 规模化硬约束（如实记录）

| 预设 | 栈参数 | 实例化峰值 | T=512 训练步 |
|---|---|---|---|
| small | 0.37M | 737 MB | 通过 |
| proto20m | 16.77M | 2241 MB | 通过 |
| p100m | 93.74M | 5799 MB | **OOM 被杀** |
| p100mw | 93.83M | 4897 MB | 通过 |
| **scale05b** | **481.65M** | **实例化 OOM** | **不可运行** |

- **0.5B 本机不可能跑**：训练态权重 + AdamW 状态需 >7 GB 可用内存，
  而提交内存常被其他进程占至 20 GB+（上限 27.87 GB）。**不得声称 0.5B 结果。**
- p100m 在 T=512 OOM，而重平衡后的 p100mw（更省内存）可通过 —— 这是减层加宽的附带收益。

### 14.6 20M 规模同协议对照（结果反转：质量升至第一）

协议：`proto20mw` 预设驱动，栈参数 16.76–16.86M 对齐，T=256、batch=8、
200 步、真实语料、`experiments/scale_compare_short.sh`。

**质量（ppl，越低越好）**

| 架构 | 栈参数 | **ppl** | 排序 |
|---|---|---|---|
| **sunnynet** | 16,755,230 | **77.90** | **1** |
| rwkv | 16,844,768 | 79.12 | 2 |
| mamba | 16,763,712 | 81.92 | 3 |
| h3 | 16,862,256 | 86.99 | 4 |
| hyena | 16,801,776 | 109.07 | 5 |

**速度（ms/token，每格独立子进程交错重测，`_scale_speed_probe.py`）**

| 架构 | ms/token | 相对 SunnyNet |
|---|---|---|
| rwkv | **0.729** | 0.63× |
| mamba | 0.922 | 0.80× |
| h3 | 0.945 | 0.82× |
| hyena | 1.066 | 0.93× |
| sunnynet | 1.152 | 1.00× |

**结论（重要，与 small 规模方向相反）**：

- **质量上 SunnyNet 在 20M 规模升至第一** —— small 规模（1.4M）是"七架构第二"，
  20M 为五架构第一。**速度劣势收窄**：small 规模同行快 20–52%，
  20M 规模收窄到 **8–37%**（hyena 仅快 7%）。方向正确，但**仍未反超**。
- **必须说清的归因**：此变化**不能全部归给"规模"**。20M 用的是减层加宽后的
  `proto20mw`（§14.3），而 small 用的是未重平衡的 `small` 预设。
  质量排名上升是**减层加宽 + 规模**两项共同作用；
  且两侧对照的架构集合（七 vs 五）、步数（600 vs 200）都不同，**不可直接相减**。
- **如实标注**：200 步**远未收敛**；`mamba` 格在训练循环内读数（2.057 ms/tok）
  明显被外部负载污染（墙钟 872 s vs 其余 370–510 s，ms/token 逐档恶化），
  **速度一律以隔离重测为准**。

### 14.7 核心扫描 / 竞争门控"写成融合 kernel"的收益上界（实测，结论：优先级低）

**问题**：把核心扫描与竞争门控写成融合 kernel 会不会显著更快？

**方法**：`experiments/_fuse_ceiling.py` 把这两段各替换为极简实现（数值不等价），
测端到端训练步。这给出"两段耗时归零"的**收益上限**，不是可落地的改写。
small 预设、T=1024、B=8、每格独立子进程、两轮交错取中位：

| 变体 | ms/token | 相对基线 |
|---|---|---|
| base（当前） | 0.1575 | — |
| 竞争门控耗时归零 | 0.1465 | −7.0% |
| 扫描耗时归零 | 0.1476 | −6.3% |
| **两者同时归零（上界）** | **0.1436** | **−8.8%** |

**结论**：

1. **收益上界只有 8.8%**。真实融合 kernel 还有自身执行开销，实际收益只会更低（估 3–5%）。
2. **不可行**：CPU 上写自定义融合 kernel 需 `torch.compile`/`cpp_extension`/triton，
   本机三者均不可用（§13.4：缺 Windows SDK 头文件、无 triton/numba）。
3. **单块剖析解释了原因**：`_compete` 占单块 14.4%、`_scan` 占 17.2%（前向），
   但**训练步的反向占约 65%**（§13.3），前向占比再高也摊不进大分母。
4. **务实结论**：融合 kernel 的性价比低于**减层加宽（已实测 12–17%）**；
   若资源有限，应优先做能落实的改动，而非追求需编译工具链的融合。
